.gitignore — навіщо він потрібен

Git за замовчуванням хоче відстежувати усе. А треба — не все.

  • Сміття оточення: venv/, __pycache__/, .idea/ — це не код, це стан твоєї машини
  • Згенеровані файли: *.pyc, білди, логи — їх завжди можна створити заново
  • Секрети: .env з паролями, токенами, ключами API
  • Важкі файли: бази даних, медіа, датасети — репозиторій роздувається назавжди
Реальний кейс Розробник закомітив .env з ключем AWS. Бот знайшов його на GitHub за 4 хвилини й підняв ферму для майнінгу.
Рахунок — кілька тисяч доларів за ніч.
І прозаїчніше Ти комітиш .idea/ — колега робить pull і йому ламає налаштування IDE. Далі — конфлікт у файлі, який взагалі не код.

А якщо файл вже в репозиторії?

Головне непорозуміння: .gitignore не діє на файли, які Git уже відстежує.

# .env вже закомічений — додали в .gitignore, # а він усе одно у змінах. Прибираємо з індексу: $ git rm --cached .env rm '.env' # цілу теку — рекурсивно: $ git rm -r --cached .idea/ # перевіряємо і комітимо $ git status $ git commit -m "chore: stop tracking .env"
--cached — це важливо Без нього git rm видалить файл і з диска. З ним — файл лишається у тебе, Git просто перестає його бачити.
Але секрет уже скомпрометований git rm --cached прибирає файл із майбутніх комітів. У старих комітах він лишається — і його видно через git log будь-кому, хто має репозиторій.
Що робити насправді
  1. Відкликати ключ / пароль і випустити новий
  2. Прибрати файл з індексу й додати в .gitignore
  3. Тільки потім — чистити історію (git filter-repo), якщо це взагалі потрібно

Чому логін і пароль більше не працюють

  • 13 серпня 2021 — GitHub повністю вимкнув автентифікацію паролем для Git-операцій
  • Причина: пароль дає доступ до всього акаунта — усі репозиторії, налаштування, білінг
  • Пароль не має терміну дії, його не можна обмежити одним проєктом і важко відкликати «частково»
  • Тому GitHub перейшов на токени й ключі: обмежені за правами, за терміном і за областю дії
Знайома помилка?
remote: Support for password authentication
was removed on August 13, 2021.
Саме її бачить кожен, хто вперше робить git push.
Ключова ідея

Доступ ≠ акаунт

Ти більше не «входиш» у GitHub з термінала. Ти видаєш конкретному пристрою або конкретному скрипту обмежений ключ, який у будь-який момент можна відкликати — не змінюючи пароль і не ламаючи решту.

Наслідок для нас Поки доступ не налаштований, git push просто не працює. Тому це — обов'язковий крок, а не «додаткова опція».

Перевірка

Рукостискання

GitHub надсилає випадкове завдання, яке можна розв'язати лише приватним ключем. Ключ при цьому не передається по мережі — передається тільки доказ, що він у тебе є.

Чому саме ed25519, а не rsa Коротший, швидший і криптографічно сильніший за rsa 2048. У всіх сучасних інструкціях GitHub — саме він. rsa побачиш у старих туторіалах.

ssh-agent: щоб не вводити passphrase щоразу

# Git Bash: запускаємо агента в цій сесії $ eval "$(ssh-agent -s)" Agent pid 1234 # Додаємо ключ — passphrase спитає один раз $ ssh-add ~/.ssh/id_ed25519 Identity added: /c/Users/user/.ssh/id_ed25519 $ ssh-add -l # що зараз в агенті $ ssh-add -D # прибрати всі ключі

git commit --amend

Найлегший випадок: щойно закомітив — і одразу побачив помилку.

# Помилка в тексті коміту $ git commit --amend -m "feat: add user login" # Забув додати файл у той самий коміт $ git add forgotten_file.py $ git commit --amend --no-edit # --no-edit = не чіпати текст коміту $ git log --oneline a1b2c3d feat: add user login ← новий хеш!
Що насправді відбувається Git не «редагує» коміт — комміти незмінні. Він створює новий коміт замість старого. Тому хеш змінюється.
Тільки до push Якщо коміт уже на GitHub, amend перепише історію, і Git відмовиться пушити:
! [rejected] main -> main (non-fast-forward)
Далі спокуса зробити push --force — і затерти роботу колег.
Золоте правило Локальна історія — твоя, можеш переписувати.
Спільна історія — недоторканна.
Уже запушив? Виправляй новим комітом або через revert.

git reset: три режими

Усі три відкочують HEAD назад. Різниця — що вони роблять зі змінами.

Команда HEAD
(історія)		 Staging Робочі файли Коли це те, що треба
git reset --soft HEAD~1 назад збережено збережено Розбити один великий коміт на кілька; переробити повідомлення разом зі складом
git reset HEAD~1
(= --mixed, за замовчуванням)		 назад очищено збережено Закомітив не ті файли — хочу перебрати, що саме додавати
git reset --hard HEAD~1 назад очищено ЗНИЩЕНО Експеримент повністю провалився — хочу чистий стан, як був
Прибрати файл зі staging git reset file.py — без хеша й без --hard. Це просто «скасувати git add», файл не постраждає.
--hard — єдина справді небезпечна Незакомічені зміни після неї не відновити нічим. Git навіть не спитає підтвердження.

reset vs revert

reset — стирає

Ніби коміта й не було

Історія переписується. Підходить, поки коміти живуть тільки в тебе на диску.

до:  A — B — C
після: A — B
revert — виправляє

Новий коміт, що скасовує старий

Історія лишається цілою — видно, що було зламано і коли це відкотили. Безпечно для спільної гілки.

до:  A — B — C
після: A — B — C — C′
# Скасувати конкретний коміт безпечно $ git revert a1b2c3d [main d4e5f6g] Revert "feat: broken payment" # Скасувати merge-коміт $ git revert -m 1 <merge-hash>
Правило одним рядком Коміт уже на GitHub і його бачили інші → тільки revert.
git reflog — рятівний круг Зробив --hard не туди? Git місяцями пам'ятає, де був HEAD:
$ git reflog
$ git reset --hard HEAD@{2}
Рятує коміти. Не рятує зміни, які не встигли стати комітом.

git stash — «поклади поки що в шухляду»

Пишеш фічу, вона наполовину готова — і тут прилітає терміновий баг на проді.

# Ховаємо незавершені зміни (-u = і нові файли) $ git stash -u -m "половина форми логіну" $ git status nothing to commit, working tree clean # Спокійно фіксимо терміновий баг $ git switch -c hotfix/payment # Повертаємось і дістаємо назад $ git switch feature/login $ git stash list stash@{0}: On feature/login: половина форми... $ git stash pop
КомандаЩо робить
git stashСховати зміни, повернути чисту робочу теку
git stash -uТе саме + нові файли, яких Git ще не бачив
git stash listПоказати всі схованки
git stash popДістати останню і видалити зі списку
git stash apply
git stash drop		Дістати, але залишити копію
Викинути схованку
Не перетворюй stash на смітник Схованки не синхронізуються з GitHub, і через тиждень ти не згадаєш, що лежить у stash@{4}. Для чогось довшого за годину — краще гілка.

Анатомія Pull Request

З чого складається
  • base ← compare — «влити feature/login у main». Найчастіша помилка новачка — переплутати напрямок
  • Conversation — обговорення й історія подій
  • Commits — усі коміти гілки
  • Files changed — той самий git diff, тільки зручний: тут і лишають коментарі
  • Checks — результати CI: ✓ passed ✕ failed
Draft Pull Request Відкривай PR одразу, ще на початку роботи, у статусі Draft. CI ганяється з першого коміту, а команда бачить, що ти робиш.
Опис, який не дратує рев'юера
## Що зроблено Додав ендпоінт /login і перевірку пароля. ## Як перевірити 1. pytest tests/test_auth.py 2. POST /login з валідними даними → 200 ## Пов'язані задачі Fixes #14 ← закриє issue #14 при merge

Merge commitусі коміти + коміт злиття
Squash and mergeуся гілка → один коміт у main часто дефолт
Rebase and mergeкоміти лягають у main без злиття

Code review

Не екзамен і не критика особистості. Це друга пара очей на код, який піде в продакшн.

Три вердикти рев'юера
Comment

Питання без вироку — «а що буде, якщо список порожній?»

Approve

Можна зливати. Дрібні побажання лишають необов'язковими (nit:)

Request changes

Є що виправити до merge. Не образа — нормальна частина процесу

На що дивитись
  • Чи працює — логіка, граничні випадки, помилки
  • Чи зрозуміло — назви й структура; чи розбереться інша людина за пів року
  • Чи безпечно — секрети, SQL-ін'єкції, дані користувача
  • Чи є тести на нову поведінку
Suggestion — коментар, який комітиться Рев'юер пише готову правку в блоці suggestion, автор тисне Commit suggestion — і вона вже в гілці.
Стиль коду не обговорюють люди Відступи, лапки, довжину рядка перевіряє лінтер у CI, а не колега в коментарях.

CI — робот, який перевіряє код за тебе

Continuous Integration: на кожен push і кожен PR автоматично ганяються тести й лінтер.

  • Ловить те, що «у мене працює» — забутий імпорт, залежність, якої немає в requirements.txt, тест, зламаний сусідньою правкою
  • Знімає суперечки про стиль — ruff сказав, що не так, і це не чиясь думка
  • Дає видимий статус у PR — червоний хрестик видно раніше, ніж рев'юер відкриє код
  • Це вже не «додатково» — на будь-якій вакансії Junior+ CI є за замовчуванням
GitHub Actions

Вбудовано в GitHub

Нічого не треба піднімати й налаштовувати окремо. Кладеш YAML-файл у теку .github/workflows/ — і воно вже працює.

Для публічних репозиторіїв — безкоштовно.

Словник workflow — файл-сценарій · job — окреме завдання на чистій віртуалці · step — один крок · action — готовий блок, який хтось уже написав

Розбираємо .github/workflows/ci.yml

name: CI on: # коли запускати push: branches: [main] pull_request: # на кожен PR jobs: test: runs-on: ubuntu-latest # чиста віртуалка steps: - uses: actions/checkout@v4 - uses: actions/setup-python@v5 with: python-version: "3.12" - run: pip install -r requirements.txt - run: ruff check . - run: pytest -q
  • on: — тригер. pull_request без параметрів = будь-який PR
  • runs-on: — GitHub піднімає чисту Ubuntu. Саме тому CI і ловить «а в мене ж працювало»
  • uses: — готовий action: checkout клонує код, setup-python ставить Python
  • run: — звичайна команда в терміналі тієї віртуалки
Найчастіша причина червоного CI Немає requirements.txt. Робот бачить рівно те, що закомічено — не пакети, встановлені локально в тебе, і не файли з .gitignore.
Кроки йдуть згори вниз і зупиняються на першій помилці.

Підсумок

Чеклист для будь-якого нового проєкту
  1. .gitignore — до першого коміту
  2. SSH-ключ налаштований, origin через git@
  3. Секрети — тільки в .env, у репозиторії — .env.example
  4. Робота — в гілках, у main — через PR
  5. ci.yml з тестами й лінтером із першого дня
